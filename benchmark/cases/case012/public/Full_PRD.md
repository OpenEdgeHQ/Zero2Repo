# lint-policy — Full Product Requirements Document

## Product overview

**lint-policy** is an opinionated Oxlint ruleset that rejects low-evidence and low-signal TypeScript and JavaScript patterns. It is the ruleset its author uses with work, projects, and a team. It reflects that taste rather than attempting to be a universal coding standard.

The product is **meant to be vendored**, not treated as a fixed registry package. There is no official published package. A consuming repository copies the plugin, reads it, and may change it to match local standards. After the initial copy, the vendored files belong to that repository.

lint-policy is first a **generic Oxlint JavaScript plugin** whose eighteen rules apply to ordinary TypeScript and JavaScript. Effect-specific architecture policy lives in a **second, opt-in plugin** so projects that do not use Effect do not inherit Effect rules. A consuming Oxlint (or Vite+) configuration registers one or both plugins, enables the desired rules, and runs the host linter against source files. Each enabled rule either reports a diagnostic on a violating construct or stays silent on an allowed construct.

A first-time integrator copies the plugin into the target repository (by hand, or by running the bundled skill copy), registers the generic plugin with Oxlint, enables every generic rule at error severity, and — only when the target depends on Effect directly, or the user asks — also registers the Effect plugin and enables its five rules. From then on, a lint run on owned source is the observable product: violating patterns fail the lint; allowed patterns do not.

This document specifies **user- and integrator-observable behavior only**. Exact published symbol names, import paths, and call spellings belong in the Interface Contract, not here. Every feature point below corresponds to behavior that exists in the finished lint-policy product. Feature points are ordered so foundational capabilities come first; a later feature point may refine an earlier one only when it says so explicitly.

## Terminology

| Term | Meaning in this PRD |
| --- | --- |
| **lint-policy** | The product: the generic Oxlint plugin, the opt-in Effect plugin, and the bundled skill that copies them into a consuming repository. |
| **Generic plugin** | The always-applicable plugin. Its published plugin name is lint-policy. It ships the eighteen generic rules listed in FP-01. |
| **Effect plugin** | The opt-in plugin. Its published plugin name is lint-policy-effect. It ships the five Effect rules listed in FP-07. It is not inherited merely because the generic plugin is registered. |
| **Host linter** | Oxlint, including the same plugin fields under lint in a Vite+ configuration. The plugins are JavaScript plugins the host loads by name and specifier. |
| **Rule** | One independently enableable check. A consuming configuration turns it on or off (and, for two generic rules, may pass options). When the rule is off, it reports nothing. |
| **Diagnostic** | A host-linter finding that identifies the offending construct and names the lint-policy or lint-policy-effect rule that fired. Its reported position starts within the construct the rule reports, not on a neighboring allowed construct; where a feature point names a narrower position, that position holds. Exact wording of the finding is the implementer’s; the **distinction** (this rule fired here, and did not fire on the allowed counterpart) is graded. |
| **Enabled at error** | The rule is on at error severity. A diagnostic from that rule makes the lint invocation fail. |
| **Known array** | A receiver the generic plugin can treat as an array from **same-file** evidence: an array literal, a direct array or tuple annotation, a `const` local alias of such a value, or a chain on such a value through `map`, `filter`, `flatMap`, `slice`, `concat`, `toSorted`, `toReversed`, or `toSpliced`. Imported factory results without a direct array or tuple annotation, unannotated parameters, type aliases of array types, and property-based array types are not known arrays. |
| **Same-file analysis** | Alias, annotation, and binding evidence that appears in the file under lint. The product does not consult a TypeScript type checker, imported type definitions, or cross-file call signatures. |
| **Transparent generic alias** | A same-file generic type alias whose body is exactly its type parameter (an identity wrapper). Applying it to a forbidden type is the same as writing that type. |
| **Vendored copy** | The plugin files as they exist inside a consuming repository after copy. That repository owns subsequent edits. |
| **Skill copy** | The bundled install-lint-policy copy entry: it places a pristine plugin tree at a relative destination and does not fetch, merge, or configure. |
| **Core capability** | A user-observable capability that reflects lint-policy’s design goal; acceptance must prove real plugin or copy behavior, not a stub. |
| **Discrimination** | An assertion’s ability to distinguish a faithful implementation from a hollow, skipped, or proxy one. |

## Public surface inventory

lint-policy is a **pair of Oxlint JavaScript plugins** plus a **copy entry** that vendors them. There is no end-user command of lint-policy’s own, no network service, and no official registry package.

The public, independently verifiable surfaces, grouped the way later feature points verify them, are:

- Copying the plugin tree into a consuming repository (default destination `tools/oxlint/lint-policy`), including refusal to proceed against an existing destination unless `--force` is passed (FP-01).
- Registering the generic plugin with the host linter and enabling any subset of its eighteen rules (FP-01). Lint of TypeScript or JavaScript source is then the observation point for FP-02 through FP-06.
- Registering the Effect plugin independently and enabling any subset of its five rules (FP-07).
- Two rule-level options: whether runtime `typeof` is allowed inside type predicates and assertion functions (default off), and which safety-comment markers count as justification for a non-const type assertion (default the single marker `SAFETY`) (FP-03, FP-05).
- Autofix for missing readable spacing only (FP-06). No other generic or Effect rule offers a fix.

Feature points below group these entries by independently verifiable capability. They do not invent additional product surfaces.

The bundled skill also instructs a host coding agent how to merge the plugin into lint configuration, pin a matching Oxlint and plugins-host version pair, enable rules, optionally enable Effect rules when Effect is a direct dependency, validate, and later update a vendored copy while preserving local customizations. Those agent procedures are instructions for a human or coding agent, not an executable merge engine shipped by this product. They are not feature points below. The copy entry, the two plugins, and the rule diagnostics are the graded product.

## Non-functional constraints

- **Form factor:** TypeScript source consumed by Oxlint as JavaScript plugins. No compiled native extension, no bundled binary, no GPU or accelerator, and no runtime network client.
- **Language floor:** Node.js 24 and the project’s documented package manager are sufficient to install from this repository and exercise a rule against a short snippet. The plugins lint TypeScript and JavaScript.
- **Platforms:** Linux, macOS, and Windows. This case’s acceptance targets Linux with a supported Node.js interpreter.
- **Hardware:** CPU-only. The mandatory execution substrate is a real host able to load the plugins into Oxlint and lint a snippet. There is no removable accelerator profile. Do not write a negative-control clause that disables the package, the interpreter, or the standard library.
- **Distribution:** Vendored source, not a versioned registry dependency of lint-policy itself. A consuming repository that already uses Oxlint installs the Oxlint plugins-host package at **exactly** the resolved Oxlint version; otherwise it installs the same current version of both. Those versions stay exact so upgrades move together. That pairing is install guidance for the host; it is not an lint-policy rule.
- **Analysis:** Same-file evidence only, as defined above. A construct that is only known to be an array, an `unknown` alias, or an Effect tagged type because of another file must not be treated as if that fact were local.
- **Determinism:** The same source, with the same rules enabled and the same options, produces the same diagnostics. There is no model and no random component.
- **Opinionated scope:** lint-policy is not a general-purpose formatter, type checker, or Effect type verifier. Spacing autofix inserts blank lines only; it does not add braces, wrap expressions, sort imports, or infer every logical group.

## Capability discrimination (global)

Every feature point below is a **core capability**. None is an accelerator-backed mandatory-substrate GPU feature. The mandatory `cpu_baseline` profile only means the plugins run on CPU; it does not license a negative control.

For every feature point:

- **Present:** Real lint-policy behavior matches the described outcomes when the host linter loads the named plugin, enables the named rule, and lints the named source (or when the copy entry is invoked on a destination).
- **Absent / hollow:** A plugin that registers no rules; a rule that always reports or never reports; a stub that matches a single canned snippet and ignores the allowed counterpart; a copy that overwrites an existing tree without `--force`; treating Effect rules as part of the generic plugin.

Cheaper proxies (a different linter’s built-in, a regex over the file text that cannot honor same-file alias evidence, or always succeeding) do **not** satisfy core capabilities. There is no approved degradation scenario that replaces the real plugins for a core capability.

## Non-goals

- Shipping an official npm package or treating the vendored tree as a locked third-party dependency.
- Inferring imported types, cross-file signatures, or running the TypeScript type checker.
- Autofixing semantic rewrites (array pipelines, reducer copies, conditional spreads, assertions, Effect tags). Only readable spacing inserts whitespace.
- Enabling the Effect plugin merely because Effect appears transitively in a lockfile. Direct manifest dependency or an explicit request is the install-skill policy; the graded Effect surface is the plugin when it is registered (FP-07).
- Implementing Oxlint’s native accumulating-spread check. The documentation pairs that native check with lint-policy’s reducer-copy rule; the native check is not an lint-policy rule. Its absence is not an lint-policy failure.
- Broadly ignoring every dot-directory in the consuming project. Recommended ignores cover known agent-tooling directories and the vendored plugin path; they are configuration advice, not plugin diagnostics.
- Fetching or three-way-merging updates inside the copy entry. The copy only copies; update merge is an agent procedure.
- Guaranteeing that every quadratic reducer, every possible tagged value, or every Effect import alias is caught. Documented out-of-scope patterns in the feature points below are allowed to pass.

## Feature points

### FP-01: Vendor and register the generic lint-policy plugin

**Public entry:** The skill copy (invoked from a consuming repository, optionally with a relative destination and optional `--force`), or a manual copy of the plugin tree. After copy, the host-linter configuration registers a JavaScript plugin whose published name is lint-policy and whose specifier points at the generic plugin entry in the copied tree, then enables any subset of the eighteen generic rules. This feature point is **getting the generic plugin into the host and making its catalog reachable**. Individual rule diagnostics are FP-02 through FP-06. The Effect plugin is FP-07.

**Normal behavior:**

- With no destination argument, the skill copy places the plugin tree at `tools/oxlint/lint-policy` relative to the current working directory. A destination argument uses that relative path instead. After a successful copy, the destination contains both the generic plugin entry and a nested Effect plugin entry, along with the vendored stylistic license and provenance files that travel with readable-spacing enforcement. No third-party stylistic plugin dependency is required.
- A successful copy reports that the plugin was copied to the destination and names the generic entry to configure. It does not edit the consuming repository’s lint configuration, does not install packages, and does not fetch a remote revision.
- Once registered, the generic plugin publishes exactly these eighteen rules, each independently enableable under the lint-policy plugin name: `no-array-filter-map`, `no-reduce-accumulator-copy`, `no-chained-type-assertions`, `no-conditional-empty-object-spread`, `no-known-value-widening`, `no-module-mocking`, `no-object-parameters`, `no-reflect-apply`, `no-reflect-get`, `no-runtime-typeof`, `no-shape-in-symbol-names`, `no-unknown-parameters`, `no-unknown-returns`, `no-unknown-type-aliases`, `no-unsafe-dictionary-type`, `no-widen-then-assert`, `require-readable-spacing`, `require-safety-comment-for-type-assertion`.
- The generic plugin does **not** publish the five Effect rules. Those exist only on lint-policy-effect (FP-07).
- Enabling a generic rule at error severity causes a later feature point’s violating snippet to fail lint with a diagnostic attributable to that rule. Leaving that rule off (or not registering the plugin) causes the same snippet to produce **no** lint-policy diagnostic from that rule, even if the construct would violate it.
- Same-file analysis applies to every generic rule that consults types, aliases, or bindings: block-scoped aliases, forward references in the same file, and transparent generic aliases are resolved; imported type definitions and cross-file signatures are not. Where a later feature point says a rule scores a type only as written (a keyword written as that keyword), a same-file alias in that position is not resolved into it.

**Boundary / error behavior:**

- If the destination already exists and `--force` is not passed, the copy refuses to overwrite, exits unsuccessfully, and leaves the existing tree unchanged. The error identifies the destination. `--force` is the only way this copy proceeds against an occupied destination: it overwrites source-overlapping plugin paths so the destination then contains the copied generic plugin entry and the nested Effect plugin entry, both loadable. Destination-only extra files that were not in the copy are neither required to vanish nor required to remain. The advertised update path is not this copy aimed at the live installation.
- An unpublished lint-policy rule name listed in host configuration together with a known enabled rule is a host-configuration concern, not an lint-policy diagnostic. On that invocation the caller observes either a host refusal that identifies the unpublished name and the loaded generic plugin, or classified lint that does not invent a diagnostic for the unpublished name. A known enabled rule is not required to emit classified findings on the same invocation that listed the unpublished name. The plugin does not invent extra rules beyond the eighteen.
- Registering the generic plugin does not enable any rule by itself. A configuration that lists the plugin but enables no lint-policy rules reports no lint-policy diagnostics.
- Source the host cannot parse is a host failure, not an lint-policy diagnostic. lint-policy does not claim to recover from broken syntax.

**Verifiable oracle:**

- Success: a copy into an empty default destination creates `tools/oxlint/lint-policy` with both plugin entries; a copy into a caller-chosen relative destination uses that path; a second copy to the same occupied destination without `--force` fails and leaves bytes unchanged; a copy with `--force` overwrites source-overlapping plugin paths so the destination contains the copied generic and nested Effect plugin entries, both loadable (destination-only extras are neither required to vanish nor required to remain); registering the generic plugin and enabling only `no-array-filter-map` reports that rule on an array-literal filter-then-map chain (FP-02) and reports **no** Effect-plugin rule; the same chain with the plugin unregistered, or with that rule omitted, produces no lint-policy diagnostic; listing an unpublished lint-policy rule name with a known enabled rule yields either a host refusal identifying that unpublished name and the loaded generic plugin, or classified lint with no invented diagnostic for that name (a known rule need not report on that invocation); enabling `no-unknown-returns` flags a same-file alias of `unknown` used as an explicit return type and does **not** flag a return type whose name is not defined in the same file (FP-04).
- Failure / absence: copy silently overwrites without `--force`; the generic plugin exposes Effect rules or fewer than eighteen generic rules; a disabled rule still fires; an unpublished name invents a nineteenth lint-policy diagnostic; imported aliases are treated as if they were defined in the file under lint; a stub reports the same diagnostic on every file regardless of which rule is enabled.

### FP-02: Reject eager array pipelines, reducer copies, and conditional empty spreads

**Public entry:** With the generic plugin registered (FP-01), enable `no-array-filter-map`, `no-reduce-accumulator-copy`, and `no-conditional-empty-object-spread` at error severity and lint TypeScript or JavaScript source. This feature point is those three collection-construction checks. None of them offers autofix.

**Normal behavior:**

- `no-array-filter-map` reports when a **known array** is chained through adjacent eager `filter` then `map`, or adjacent eager `map` then `filter`, including optional chaining, non-null assertions, computed string method names, and an extra trailing `filter` on an already-flagged pair (each adjacent pair is its own diagnostic). A known array includes an array literal, a direct array or tuple annotation on a parameter or binding (including a readonly array, `Array` of a type, and `ReadonlyArray` of a type), a `const` local alias of such a value, and a chain on a known array through `map`, `filter`, `flatMap`, `slice`, `concat`, `toSorted`, `toReversed`, or `toSpliced`.
- The same rule stays silent for: iterator pipelines (`values` then `filter`/`map`, `Iterator.from`, or a parameter typed as an iterator object); a single `flatMap`; `map` then `map`; `filter` then `filter`; `filter` and `map` as separate statements; a custom object that happens to have `filter` and `map` methods; an unknown or imported receiver; an unannotated parameter; a type alias of an array type; a `let` or `var` alias of an array literal even when never reassigned; a binding that was reassigned; a dynamically computed method name that is not a string literal.
- `no-reduce-accumulator-copy` reports on an inline `reduce` or `reduceRight` callback (including index parameters, defaulted accumulator parameters, bracket access to `reduce`, and a `const` local alias of the accumulator) when the callback copies accumulated state by: global `Object.assign` with an object-literal target and the accumulator as a source; global `Array.from` of the accumulator; or, when the initial value is a locally evident array, accumulator calls to `concat`, `slice`, `toSpliced`, `toSorted`, `toReversed`, or `with`.
- The same rule stays silent for: mutating a fresh local accumulator and returning it; `Object.assign` that uses the accumulator as the target; copying an individual input item rather than the accumulator; copying a nested property of the accumulator; a local alias of `Object.assign` or `Array.from`; `concat` on a string initial value or an unknown custom collection; named callbacks declared outside the call; nested functions or snapshot closures that copy; a shadowed inner binding named like the accumulator; a locally shadowed `Object` or `Array`; a `let` or `var` alias of the accumulator even when never reassigned; a reassigned alias of the accumulator; array or object **spreads** inside the reducer (those are owned by Oxlint’s native accumulating-spread check, not this rule).
- `no-conditional-empty-object-spread` reports an object spread whose operand is a conditional whose true branch or false branch is an empty object literal (used to omit a field). A conditional that is not spread, a spread of a non-conditional value, and an object without that pattern stay silent.

**Boundary / error behavior:**

- None of these three rules rewrites the source under the host’s fix mode. A configuration that requests fix still leaves the violating construct in place and still reports it.
- Receivers that are not known arrays are not guessed. A `filter` then `map` chain on `fetchUsers()` or on an untyped parameter is allowed.
- Reducer method names are syntactic. The rule does not prove the receiver is a runtime array; it also does not claim every quadratic reduction is absent.

**Verifiable oracle:**

- Success: linting `[].filter(active).map(email)` with `no-array-filter-map` enabled fails with that rule; `users.slice().filter(active).map(email)` on a `const` local array also fails (slice keeps the receiver a known array); a binding with a direct `User[]` annotation initialized from `loadUsers()` fails; `users.values().filter(active).map(email).toArray()` on a local array succeeds; `users.filter(active)` and `users.map(email)` as two statements succeed; a same-file type alias of an array type used as a parameter annotation succeeds; `let users = []; users.filter(active).map(email)` succeeds; linting `items.reduce((acc, item) => Object.assign({}, acc, { [item.id]: item }), {})` with `no-reduce-accumulator-copy` enabled fails with that rule; `const alias = acc` copied with `Object.assign({}, alias)` inside that inline reduce fails, and `let alias = acc` with the same copy succeeds; the same reduce that `push`es onto `acc` and returns `acc` succeeds; `acc.concat([item])` with a `[]` initial value fails, and `acc.concat(item)` with a string initial value succeeds; `Object.assign` of a nested property of `acc`, and a local alias of `Object.assign` used inside the reducer, succeed; linting `{ ...(value !== undefined ? { value } : {}) }` with `no-conditional-empty-object-spread` enabled fails with that rule; `{ ...values }` and `condition ? { value } : {}` (not spread) succeed; fix mode does not rewrite any of the three failing snippets.
- Failure / absence: iterator pipelines are flagged; unknown receivers are flagged; mutating reducers are flagged; spreads inside reduce are flagged by this rule; conditional empty spreads are rewritten to assign `undefined`; fix mode silently “passes” by changing semantics.

### FP-03: Keep type evidence; justify remaining assertions

**Public entry:** With the generic plugin registered (FP-01), enable `no-chained-type-assertions`, `no-known-value-widening`, `no-widen-then-assert`, and `require-safety-comment-for-type-assertion` at error severity and lint TypeScript source. The safety-comment rule accepts an optional list of marker strings; when omitted, the sole marker is `SAFETY`. This feature point is type-evidence discipline. Same-file analysis (FP-01) applies.

**Normal behavior:**

- `no-chained-type-assertions` reports nested `as` assertions and nested angle-bracket assertions, including parenthesized links in the chain and a mix that ends in a non-const assertion after `as const`. A single assertion is allowed. A chain made only of `as const` (including a parenthesized `as const` then another `as const`) is allowed.
- `no-known-value-widening` reports a **known** expression flowing into an explicit `unknown`, `object`, anonymous-object, or open-dictionary target — as a variable annotation, assignment, return annotation, class field initializer, or assertion — including a known argument passed to a local type predicate whose parameter is written as the keyword `unknown` (or as a union containing that keyword). A predicate parameter written as a same-file alias of `unknown`, or as a union that contains such an alias but not the keyword itself, is not this target. On those five non-predicate vehicles, known is an object literal with concrete keys, a numeric or array literal, or a `const` local alias of such a literal. A local whose only same-file evidence is a precise annotation (no literal initializer) is known only as that type-predicate argument.
- The same widening rule stays silent for: empty dictionary accumulators assigned to an open `Record`; finite-key `Record` targets (a union of literal keys, or a named key alias that is a finite union); `satisfies` of an open record (keys preserved); a known object assigned to a **named** interface or named alias with those finite keys; an imported type name used as the annotation (not resolved); a type predicate called with a still-unparsed `unknown` argument; an unreassigned `let` or `var` alias of a literal; a local whose only same-file evidence is a precise annotation (no literal initializer) used as a variable annotation, assignment, return annotation, class field initializer, or assertion.
- `no-widen-then-assert` reports an immutable local `const` that first stores a known value under the keyword `unknown`, `any`, or `object`, and later asserts that same binding to a narrower type in the same function (or at top level). A store annotated with a same-file alias of `unknown` or `object` instead of the keyword is not this store; that store still widens under `no-known-value-widening`. A broad record here is a written annotation that is the language dictionary utility `Record`, with key type argument `string` and value type argument `unknown` or `any`: storing a known value under that annotation and later asserting the same binding to a narrower type with named fields, in the same function or at top level, reports this rule, and the same store with no later narrower assertion does not. A dictionary whose values are a named type, including the open `Record<string, Command>` already scored for widening, is not this store. Widening without a later narrower assertion is allowed. Asserting a binding that was already `unknown` at the boundary (never a known value in this file) is allowed.
- `require-safety-comment-for-type-assertion` reports a non-const `as` or angle-bracket assertion that lacks a nearby, non-empty justification. A justification is a comment immediately before the assertion’s owning statement (including immediately above an `export` of that statement), a comment separated from that owning statement only by a blank line, or an inline comment on the assertion, whose text contains a configured marker, a colon, and at least one non-whitespace character after the colon. `as const` and angle-bracket `const` assertions do not require a comment. A comment after the assertion is too late. A comment that is not a configured marker, a marker with nothing after the colon, or a marker that is only whitespace after the colon, does not count.
- A supplied markers list names one or more markers, and only those markers count. Multiple markers are alternatives: any one of them with a non-empty justification is enough. An omitted list is treated as the default: the single marker `SAFETY`. A list that names no marker is neither that supplied list nor the omitted-list default, so it is not scored: this feature promises neither a diagnostic for it nor that the host accepts it. Marker matching is the implementer’s as long as the configured strings, including ones that contain a plus sign, are recognized as whole markers.

**Boundary / error behavior:**

- These rules do not offer autofix.
- Same-file non-generic aliases, including block-scoped aliases, that resolve to `unknown`, `object`, or an open dictionary are treated as those targets on the five non-predicate widening vehicles. They are not resolved into the keyword in the two keyword-only positions above: a type-predicate parameter of `no-known-value-widening`, and the store annotation of `no-widen-then-assert`. A same-file transparent generic identity application is treated as a widening target when it resolves to an open dictionary; applying it to `unknown` or `object` is not promised as those targets and is not scored. Names not defined in the file are not.
- The safety-comment rule does not grade the **truth** of the justification, only that a configured marker and a non-empty justification are present before the assertion.

**Verifiable oracle:**

- Success: `input as unknown as User` fails `no-chained-type-assertions`; `input as User` succeeds; `({ id: 1 } as const) as const` succeeds and `({ id: 1 } as const) as User` fails; `{ start: startCommand }` annotated as `Record<string, Command>` fails `no-known-value-widening`, while the same literal with `satisfies Record<string, Command>`, or assigned to a named interface that declares `start`, or an empty `{}` annotated as that open record, succeeds; a `const` alias of `{ start: startCommand }` assigned to that open record fails, and a `let` alias of the same literal succeeds; a same-file transparent generic alias applied to that open record, used as the annotation of the known literal, fails; a local whose only same-file evidence is a precise annotation (no literal initializer) assigned to that open record succeeds; `isString("known")` for a local `unknown` type predicate fails, `isString(known)` when `known` is that annotation-only local fails, and `isString(input)` when `input` is `unknown` succeeds; a `const` known object stored as `unknown` then asserted to `{ readonly id: string }` fails `no-widen-then-assert`, while storing as `unknown` without a later assertion, or asserting a declared `unknown` input, succeeds; a `const` known object stored as `Record<string, unknown>` or as `Record<string, any>` then asserted to `{ readonly id: string }` fails `no-widen-then-assert`, while that store with no later assertion succeeds, and the same known object stored as `Record<string, Command>` and then asserted to `{ readonly id: string }` does not fail `no-widen-then-assert`; `value as UserId` with no comment fails `require-safety-comment-for-type-assertion`; the same assertion with `// SAFETY: parsed before branding.` immediately above succeeds; with markers set only to `INVARIANT`, an `INVARIANT` justification succeeds and a `SAFETY` justification fails; `[1, 2] as const` succeeds without a comment.
- Failure / absence: every assertion is flagged, including `as const`; empty dictionaries are flagged as widening; type predicates on `unknown` inputs are flagged; safety comments after the statement count; default markers include nothing or require a marker other than `SAFETY`; chained const-only assertions are flagged.

### FP-04: Reject unknown, object, and unsafe dictionary contracts

**Public entry:** With the generic plugin registered (FP-01), enable `no-object-parameters`, `no-unknown-parameters`, `no-unknown-returns`, `no-unknown-type-aliases`, and `no-unsafe-dictionary-type` at error severity and lint TypeScript source. This feature point is **explicit contracts** that erase structure. Same-file analysis (FP-01) applies. None of these rules offers autofix.

**Normal behavior:**

- `no-object-parameters` reports a function, method, or function-type contract parameter whose same-file type is `object`, a union containing `object`, or a scoped or transparent generic alias that resolves to `object`. Defaulted parameters and destructured parameters are included. A named interface or object type with members is allowed. A generic type **parameter** (including one constrained with `extends object`) is allowed. A type parameter that merely **shadows** a same-file `object` alias is allowed. An `object` alias that is not used as a parameter is not this rule’s concern.
- `no-unknown-parameters` reports a parameter whose **written** type is `unknown` or a union containing `unknown`, except: a parameter literally named `cause` whose type is `unknown` or a union containing `unknown`; and the **exact subject** of a type predicate or assertion function (`value is T` or `asserts value is T`), including arrow, declared, and method forms. Additional `unknown` parameters on the same function are still reported. A parameter typed as `string | number` is allowed. A same-file alias of `unknown`, or a transparent generic application of `unknown`, used as a parameter is not this rule’s concern.
- `no-unknown-returns` reports an **explicit** function, arrow, declared-function, method, or function-type contract whose same-file resolved return type is `unknown`, `Promise<unknown>`, or `PromiseLike<unknown>`, including unions containing `unknown` and scoped or transparent generic aliases that resolve to those. Inferred returns (no annotation) are allowed. A generic return of the function’s own type parameter is allowed even if a same-file alias named the same as that parameter is `unknown`. Returning a named object type that has an `unknown` field is allowed. A return type name that is not defined in the same file is not treated as `unknown`.
- `no-unknown-type-aliases` reports a same-file type alias whose resolved type is `unknown` (including unions containing `unknown` and transparent generic applications such as identity of `unknown`). An alias of a structured type that **contains** `unknown` as a field or as a type argument of a non-transparent wrapper (for example a box of `unknown`) is allowed. An alias of `string` is allowed.
- `no-unsafe-dictionary-type` reports dictionary **value** contracts based on `unknown`, `any`, `object`, `{}`, or semantic equivalents (including `NonNullable<unknown>`, `Readonly<unknown>`, brand-only empty types written as the object type `{ readonly mark?: never }` or `{ tag?: never }`, the same-file interface `interface Mark { readonly mark?: never }` or `interface Mark { tag?: never }`, and the same-file alias `type Mark = { readonly mark?: never }` or `type Mark = { tag?: never }` of that object type, empty interfaces, and unions or wrappers that still resolve to those), written as `Record`, index signatures, mapped dictionaries, or `Readonly`/`Partial`/`Required`/`Pick`/`Omit` of such a dictionary. Each of those brand-only spellings has at least one member and every member is an optional property of type never. The property identifier is not part of the contract. One spelling carries a `readonly` modifier and one spelling does not. Those brand-only spellings are reported by `no-unsafe-dictionary-type` when each is the value of a dictionary written as `Record`, an index signature, a mapped dictionary, or `Readonly`, `Partial`, `Required`, `Pick`, or `Omit` of such a dictionary. A value that also has a member which is not an optional property of type never, such as `{ id: string; mark?: never }`, stays an allowed named data type and is not reported. A same-file alias of an unsafe dictionary is reported where that dictionary is written; a plain later use of the alias, such as a variable annotation, is not required to report. A `Readonly`, `Partial`, `Required`, `Pick`, or `Omit` application to an unsafe dictionary is itself reported, whether the dictionary is written as its argument or is a same-file alias of an unsafe dictionary, and also when those wrappers are nested: a diagnostic of this rule starts at the name of the outermost such wrapper. A finding on the inner dictionary, on an inner wrapper, or on the alias may also appear; it does not replace the finding at the wrapper name. Allowed: dictionaries whose values are a named command or data type; nested objects that themselves contain `unknown` fields; `Map` / `ReadonlyMap` / `WeakMap`; a **generic constraint** such as a type parameter extending `Record<string, unknown>` (including on functions, classes, and type aliases); a locally shadowed `Record` type that is not the language dictionary; an imported `Record`.

**Boundary / error behavior:**

- Where these rules resolve aliases or wrappers, they do so only in the same file, including inner functions that declare an alias used by a nested function, and forward references. A later inner alias does not leak into an outer function that never declared it. `no-unknown-parameters` does not resolve aliases.
- A plain later use of a same-file alias of an unsafe dictionary, such as a variable annotation, is not required to be reported again. The obligation is that an unsafe dictionary is diagnosed where it is written (for a wrapped dictionary, the finding at the outermost wrapper name counts), and that every wrapper application above is diagnosed at the outermost wrapper name, including when the wrapped dictionary is a same-file alias.
- These rules do not rewrite source under fix mode.

### FP-05: Reject runtime typeof, Reflect apply/get, and module mocking

**Public entry:** With the generic plugin registered (FP-01), enable `no-runtime-typeof`, `no-reflect-apply`, `no-reflect-get`, and `no-module-mocking` at error severity and lint TypeScript or JavaScript source. `no-runtime-typeof` accepts an optional `allowInTypeGuards` flag; when omitted or false, the flag is off. This feature point is **runtime and test seams**. None of these rules offers autofix.

**Normal behavior:**

- `no-runtime-typeof` reports a `typeof` check that is not an **existence probe**. An existence probe compares `typeof` to the string `"undefined"` (either operand order, with `===`, `!==`, `==`, or `!=`). Ad hoc representation checks such as `typeof input === "string"`, or `typeof input === undefined` (the value `undefined`, not the string), are reported.
- When `allowInTypeGuards` is true, a `typeof` check that sits **directly** in a type predicate or assertion function (the function’s return type is `value is T` or `asserts value is T`) is allowed. Nested inner functions inside that predicate still report. Ordinary functions that are not predicates still report, even with the flag on. When the flag is false or absent, predicates report like any other function.
- `no-reflect-apply` reports a call to global `Reflect.apply` (including computed string access to `apply`). A call to `operation.apply(...)`, a call to `Reflect.get`, a locally shadowed `Reflect` object, or a parameter named `Reflect` is allowed.
- `no-reflect-get` reports a call to global `Reflect.get` (including computed string access to `get`). Ordinary property access, `Reflect.set`, and a shadowed `Reflect` are allowed.
- `no-module-mocking` reports Vitest or Jest `mock`, `doMock`, and `unstable_mockModule` calls on the real testing namespace — including `vi.mock`, `jest.mock`, computed `doMock`, `jest.unstable_mockModule`, and the same methods after a named import of `vi` from the `vitest` module or of `jest` from `@jest/globals` (including when that import is aliased locally). Allowed: constructing a real in-memory collaborator; `spyOn`; a locally created object named `vi` or a parameter named `jest` that happens to have `mock`; an import of a similarly named helper from a **project** module rather than from `vitest` or `@jest/globals`.

**Boundary / error behavior:**

- These rules do not consult a type checker to prove that `Reflect` is the language global beyond same-file shadowing. A file that does not shadow `Reflect` treats `Reflect.apply` / `Reflect.get` as the global.
- `allowInTypeGuards` defaults to **false**. The quantity is scored: a configuration that omits the option must behave as false.
- Module mocking does not report `spyOn` and does not report non-mock APIs on the same namespaces.

**Verifiable oracle:**

- Success: `if (typeof input === "string") use(input)` fails `no-runtime-typeof`; `typeof document === "undefined"`, `typeof globalThis.crypto === "undefined"`, and `typeof localStorage !== "undefined"` succeed; with default options, a type predicate that uses `typeof value === "string"` fails; with `allowInTypeGuards` true, that predicate succeeds and a non-predicate `parse` that uses `typeof` still fails, and a nested arrow inside the predicate still fails; `Reflect.apply(operation, owner, args)` fails `no-reflect-apply` while `operation.apply(owner, args)` succeeds; `Reflect.get(owner, key)` fails `no-reflect-get` while `owner[key]` and `Reflect.set` succeed; a local `const Reflect = { apply() { return 1; } }; Reflect.apply()` succeeds; `vi.mock("./user-store")` and `jest.mock("./user-store")` fail `no-module-mocking`; `import { vi as mockVi } from "vitest"; mockVi.mock("./user-store")` also fails; `vi.spyOn(store, "save")` and `new InMemoryUserStore()` succeed.
- Failure / absence: existence probes are flagged; the default allows `typeof` in predicates; shadowed `Reflect` is flagged; `spyOn` is flagged as module mocking; aliased Vitest `mock` is missed; `allowInTypeGuards` true also permits `typeof` in ordinary parsers.

### FP-06: Ban shape in locally owned names; require readable spacing

**Public entry:** With the generic plugin registered (FP-01), enable `no-shape-in-symbol-names` and `require-readable-spacing` at error severity and lint TypeScript or JavaScript source. Readable spacing is the only generic rule that autofixes. It takes **no** options; local taste is expressed by editing the vendored rule, which is outside this feature’s scored surface. This feature point is naming and whitespace.

**Normal behavior:**

- `no-shape-in-symbol-names` reports the case-insensitive substring `shape` in **locally owned** names: variable bindings, functions, classes, interfaces, type aliases, locally declared property names, private names, and JSX names (including a property named `shape` on a local type, an interface named `UserShape`, and a local binding named `shape` used as a computed key). Static member names such as `schema.shape` or `outer.inner.shape` are allowed, including on a local binding and on assignment, because that member name belongs to the value’s owner and cannot be renamed locally. An ordinary property such as `owner.id` is allowed.
- `require-readable-spacing` reports missing blank lines in these situations, and under the host’s fix mode **inserts** those blank lines without otherwise rewriting the file:
  - between any two adjacent top-level non-import statements (including `const` then `const`, `export const` then a documented `export type`, interface then class, and adjacent function, class, interface, or type declarations);
  - after imports before the first non-import;
  - before `return`, `if`, `switch`, `try`, `for`, `while`, and `do` when they follow other statements in a block;
  - after a block-like statement before the next statement;
  - around multiline `const`, `let`, `var`, and `using` bindings;
  - around a nested `function`, `class`, `interface`, or `type` declaration and its neighboring statements.
- The same spacing rule **preserves**: adjacent import lines with no required blank line between them; adjacent short variable declarations inside a function (two one-line `const` bindings stay grouped); adjacent function overload signatures together with their implementation; documentation comments attached to the following declaration (the inserted blank line goes **before** that documentation, not between the documentation and the declaration); existing extra blank lines (the rule never removes blank lines). A compact function body that is a single statement, such as `function f() { return 1; }`, stays on one line. Adjacent `switch` case clauses with no blank line between them stay compact.
- After a successful fix pass, a second lint or fix pass on the same files reports no spacing diagnostics and does not change the files further. The rule inserts whitespace only: it does not add braces, wrap expressions, sort imports, or enable a competing formatting preset.

**Boundary / error behavior:**

- `no-shape-in-symbol-names` does not offer autofix (renaming is a semantic choice).
- `require-readable-spacing` does not delete blank lines even when a team would prefer denser code. Density preferences are not scored.
- Host formatters may run after this fix; this rule does not claim to own indentation or wrapping.

**Verifiable oracle:**

- Success: `const shape = 1`, `function shapeOf() {}`, `interface UserShape { id: string }`, `type PayloadShape = { id: string }`, and `type Payload = { shape: string }` each fail `no-shape-in-symbol-names`; `schema.shape.id` on a declared external schema succeeds, as does `local.shape` on a local binding and assignment to `schema.shape`; two top-level `const` declarations with no blank line between them fail `require-readable-spacing`, and fix inserts exactly one blank line between them; `export const a = 1` immediately followed by `/** B docs. */ export const b = 2` fails, and fix inserts a blank line **before** the documentation so the documentation stays attached to `b`; inside a function, `const a = 1; const b = 2;` then `return a + b` keeps the two short bindings adjacent and inserts a blank line before `return`; a `while` (or `if`, `switch`, `try`, `for`, or `do`) that follows another statement in a block also receives a blank line; `function f() { return 1; }` stays on one line; `function f() { const a = 1; return a; }` still receives a blank line before `return`; adjacent `case` clauses stay compact; adjacent overload signatures stay grouped; a second fix pass leaves the file bytes unchanged; running the host linter with only this rule enabled on those two-declaration files fails before fix and succeeds after fix.
- Failure / absence: `schema.shape` or `local.shape` is flagged; `shape` in a local type or interface name is allowed; a single-statement compact body is rewritten; fix removes blank lines; fix inserts a blank line between a documentation comment and its declaration; overloads are split; a second fix pass keeps rewriting; spacing is reported but `--fix` does not change the file.

### FP-07: Opt-in lint-policy-effect plugin

**Public entry:** Register a second JavaScript plugin whose published name is lint-policy-effect and whose specifier points at the Effect plugin entry (nested under the vendored tree’s `effect` entry). Enable any subset of its five rules at error severity and lint TypeScript or JavaScript source. This feature point is **Effect architecture policy**. It does not load unless this second plugin is registered (FP-01’s generic plugin alone is not enough). None of these rules offers autofix.

The five rules are exactly: `no-manual-effect-error-tag`, `no-manual-tag-comparison`, `no-manual-tagged-construction`, `no-service-constructor-imports`, `prefer-effect-match`.

**Normal behavior:**

- These checks are identifier-exact for Effect and Match. They recognize `Effect.catch`, `Effect.catchAll`, and `Effect.catchIf`, and `Match.when` / `Match.not`, when those names are written as such. They do not resolve import aliases of Effect or Match and do not prove that a similarly named object came from Effect.
- `no-manual-tag-comparison` reports a direct equality or inequality comparison (`==`, `===`, `!=`, `!==`) of a `_tag` member (including computed `"_tag"` and either operand order) against a string literal, and a `switch` whose discriminant is `_tag` (including computed `"_tag"`). Allowed: `Predicate.isTagged`, `Match` tag handlers, comparisons against a different member such as `status`, a `_tag` comparison to a variable, a non-string, or a template, and `_tag` comparisons **inside** a broad Effect catch handler (that case belongs to the next rule, not this one).
- `no-manual-effect-error-tag` reports `_tag` comparisons against a string literal and `_tag` switches **in** an inline handler function passed as an argument of `Effect.catch`, `Effect.catchAll`, or `Effect.catchIf`. A comparison or switch of `error._tag` is the tagged-error case; a comparison or switch of `error.reason._tag` is the tagged-reason case. The two cases are distinguishable diagnostics. The finding identifies that comparison or switch, not the `Effect.catch…` call or the handler function around it. Allowed: the same `_tag` comparison **outside** those handlers; `Effect.catchTag`; a `catchTag` handler that then inspects a nested `reason._tag` (selective catch is already in use). A `_tag` comparison that sits in a nested inner function inside that handler is not promised as a catch-handler diagnostic and is not scored.
- `no-manual-tagged-construction` reports an object literal that assigns a **string literal** to `_tag` (including computed `"_tag"`). Allowed: object patterns passed directly to `Match.when` or `Match.not`; constructors such as `Ready.make({ value })` or `new NotFound({ id })`; an object whose `_tag` value is a **variable**, not a string literal.
- `prefer-effect-match` reports a chained ternary whose tests are equality or inequality comparisons (`==`, `===`, `!=`, `!==`) of **the same value** (the compared expressions match as written) against literals (including literal templates with no interpolations), in either operand order, when the false branch is another such ternary of that same value. A single ternary is allowed. A ternary that only nests another ternary in its true branch is allowed. Nested ternaries that test **different** values are allowed. Nested ternaries that are not those literal comparisons are allowed. The rule does not infer types or prove exhaustiveness.
- `no-service-constructor-imports` reports a **named** import whose imported name matches `make` immediately followed by an uppercase letter, when the module specifier is project-relative (`./` or `../`) and the file under lint is **not** a test or spec file. The finding identifies the offending imported name (its named import specifier), not the whole import declaration or its module specifier. Test or spec files are those whose path matches a `.test.` or `.spec.` suffix with a JavaScript or TypeScript (optionally JSX) extension, including the `c`/`m` module variants. Allowed: the same named import in a test or spec file; package or path-alias specifiers (not relative); default imports; a relative import whose name does not match that `make`+uppercase pattern (for example `makeissueService` with a lowercase letter after `make`); a static constructor such as `WorkspaceName.make` in an expression (this rule is about imports, not calls).

**Boundary / error behavior:**

- Registering only the generic plugin, or registering lint-policy-effect but enabling none of its rules, produces no lint-policy-effect diagnostics even on source that would violate them.
- Relative `makeService` imports in application files are reported; the rule does not rewrite them to Layer imports (no autofix).
- Package-alias imports of `make…` constructors are a documented limitation: they are not reported. That limitation is scored as allowed, not as a miss the implementer must close.
- Identifier spelling is scored: `Effect.catch` is a catch handler; a renamed binding is not.
